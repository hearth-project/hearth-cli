# 记忆功能路线图

[English](../en/memory-roadmap.md) · [返回 README](../../README.zh-CN.md)

> 状态：**M1 已完成，M2 进行中**（见 [CHANGELOG](../../CHANGELOG.md) 的 Unreleased）。已经可用：会话卡片、本地 FTS5 索引、`hearth recall`、`hearth memory remember|forget|list`、MCP `recall` / `remember` / `forget`，以及 Codex 和 Claude Code 的提问前 hook。尚未完成：`hearth memory review`、提议事实的确认流程、常驻画像受管块、Comate，以及 M3 全部内容；排期见 [开发路线图](https://github.com/hearth-project/hearth-cli/issues/1)。
>
> Hearth 是 agent 的**随身工作现场**（会话、skills、凭证、环境跟着你走）；这份文档描述怎么在此基础上加上**长期记忆**。

## 目标

1. **自动调用。** agent 在日常工作中自己用上记忆，不需要用户说「去查一下」。
2. **跨 agent、跨机器。** Codex 里做过的事，Claude Code 也知道；A 机器上的经验，B 机器上可用。
3. **快。** 记忆检索在 agent 的关键路径上，本地检索 p95 < 20 ms，hook 整体（含进程启动）< 100 ms，检索路径上不走网络。
4. **不破坏端到端加密。** 服务器仍然只存密文，检索全部在客户端完成。
5. **说法与实现一致。** 长期保存的是体积很小的「记忆」，对话正文仍按现有策略过期。

## 记忆是什么：三类内容

| 类型 | 内容 | 来源 | 大小 | 保留 |
| --- | --- | --- | --- | --- |
| **会话卡片** | 每段对话一张：标题、目标、结论、改过的文件、用过的命令、遇到的报错和解决办法、机器、时间 | 后台进程从对话中抽取 | 约 1–2 KB / 段 | 永久（体积小） |
| **事实与习惯** | 「提交前总要跑 `make lint`」「这个仓库的 CI 跑在 H800 上」「回复用中文」 | agent 在对话中提议，用户确认；或用户直接说「记住……」 | 每条几十到几百字节 | 永久，可删除 |
| **对话正文** | 完整的对话记录 | 现有同步 | 大 | 按现有过期策略 |

检索默认只查前两类（小、快、信息密度高）；需要细节时再按卡片里的会话 id 取正文片段。

## 架构

```text
              agent（Codex / Claude Code / Comate）
   ┌───────────────┬──────────────────┬───────────────────────┐
   │ ① 常驻画像     │ ② 自动注入（hook）│ ③ 主动检索（MCP 工具） │
   │ 指令文件受管块  │ 每次提问前取 top-3 │ recall / remember      │
   └───────┬───────┴─────────┬────────┴───────────┬───────────┘
           └─────────────────┼────────────────────┘
                     本地记忆索引（SQLite FTS5，毫秒级）
                             ▲  后台进程增量更新
                 卡片、事实（加密）◀──同步──▶ Hearth 服务器（只存密文）
```

### 1. 本地索引：快的关键

- **所有机器都下载全部卡片和事实，在本地建索引。** 1 万段对话的卡片约 10–20 MB，可以全部放在本地；检索不访问服务器。
- **索引用 SQLite FTS5**（服务端已经在用 SQLite，不增加依赖）：BM25 排序；中文、日文用 trigram 分词，英文按词。字段加权：标题、结论、报错 > 命令、文件 > 其他。
- **后台进程增量维护**：新卡片一到就写入索引；检索进程只读，不等待同步。
- **结果加权**：BM25 分数再乘以时间衰减（最近的更相关）和当前上下文加成（同一个仓库、同一种机器）。
- **目标性能**：10 万条记录 p95 < 20 ms；`hearth recall` 是 Go 程序，冷启动约 5 ms。
- **第二阶段**：可选向量检索（本地小模型，或用户自己配置的 embedding 服务），和 BM25 混合排序；默认关闭，不影响速度和隐私。

### 2. 卡片怎么来

- **确定性抽取（默认，免费、快）**：后台进程读同步的对话，抽出标题、用户第一个请求、最后的结论段、改动的文件路径、执行过的命令、报错行和随后的修复。不调大模型。
- **agent 写的摘要（可选，质量更高）**：对话结束时，agent 通过 MCP 工具 `remember_session` 写一段总结，替换确定性卡片里的结论部分。
- **上传前扫描**：卡片和事实上传前做凭证扫描（复用现有规则），命中的不入库。

### 3. 深度融合到 agent：三条路径叠加

| 路径 | 怎么做 | 自动程度 | 适用 |
| --- | --- | --- | --- |
| **① 常驻画像** | 把最重要的事实与习惯（≤ 1 KB）写进各 agent 的指令文件受管块（`AGENTS.md`、`CLAUDE.md`、Comate 规则），每次会话开头就在上下文里 | 完全自动，零延迟 | 所有 agent |
| **② 提问前自动注入** | 在 agent 提供的提问前 hook 里运行 `hearth recall --hook`，把和这次提问最相关的 3 条记忆作为附加上下文注入 | 完全自动，不依赖模型判断 | 有这类 hook 的 agent（如 Claude Code 的 `UserPromptSubmit`）；其他 agent 的 hook 能力需逐个确认 |
| **③ 主动检索** | MCP 工具 `recall(query)` 返回排好序的片段（会话 id、时间、机器、摘录）；`remember(fact)` / `forget(id)` 维护事实。画像里写明「遇到报错、不熟悉的仓库或之前做过的事时先 recall」 | 由模型决定何时调用 | 所有支持 MCP 的 agent |

三条路径共用同一个本地索引。① 保证习惯始终生效，② 在支持的 agent 上实现真正的自动回忆，③ 覆盖其余场景和需要细节的情况。

**控制注入成本**：hook 注入有相关度阈值，低于阈值不注入；每次最多 3 条、约 600 字；画像不超过 1 KB。

### 4. 记录习惯：确认后才生效

- agent 在对话中发现值得记住的事（用户纠正了它、反复出现的做法），调用 `remember` 提议，标注范围（只对这个仓库 / 所有项目 / 某类机器）。
- 用户在对话里确认，或在 `hearth memory review` / Web 控制台里批量确认、修改、删除。
- 和现在 `propose_setup_step` 的流程一样：agent 提议、用户决定，服务器不调大模型，也看不到内容。

### 5. 团队记忆（第三阶段）

- 事实可以标记为团队共享（例如「这个集群的 NCCL 要设 `NCCL_IB_HCA=mlx5`」），用团队密钥加密，团队成员的索引里都有。
- 会话卡片默认只属于个人，不共享。

## 隐私与控制

- 卡片、事实、本地索引都是加密同步的；本地索引文件权限 0600。
- `hearth memory forget <id>`、按会话删除卡片、`[memory] enabled = false` 整体关闭；上传选择（`config.toml` `[backup]`）同样适用于卡片。
- 被注入的记忆在 hook 输出里标明来源（会话 id、日期），用户能看到 agent 为什么知道某件事。

## 里程碑

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **M1 检索** | 会话卡片确定性抽取与同步；本地 FTS5 索引；`hearth recall` 命令；MCP `recall` 工具 | 1 万段对话上 p95 < 20 ms；能搜到其他机器、其他 agent 的对话 |
| **M2 自动化** | 常驻画像受管块；`remember` / `forget` / `hearth memory review`；Claude Code 提问前 hook 自动注入；Codex 等其他 agent 的 hook 能力逐个接入 | 不提示的情况下 agent 能用上一台机器上的结论；注入延迟 < 100 ms |
| **M3 质量与团队** | agent 写的会话摘要；可选向量混合检索；团队共享事实；控制台查看和编辑记忆 | 检索命中率、被引用率可在控制台看到 |

## 待确认的问题

- Codex、Comate 是否提供提问前 hook；没有的话，只靠常驻画像 + MCP 工具，效果需要实测。
- trigram 分词对中英混合的代码、报错文本的效果，需要用真实对话评估，必要时换成自定义分词。
- 卡片的抽取规则需要在真实对话上迭代，避免抽出噪声（长日志、大段代码）。
