# Changelog

## Unreleased

- Workspace made after logging in (shared accounts): commands inside it reported "not logged in" and asked for an email although `~/.hearth` was logged in as the same person, and running `hearth setup` there made a second device on the same machine whose daemon competed with the first ("session is leased by another device").
  - `hearth onboard status` / `hearth status` propose `hearth init --move-login <dir>` (no password) when `~/.hearth`'s account is the workspace's local identity, ask when nothing says whose workspace it is, and never offer another person's login; the JSON has `home_login`.
  - `hearth setup` in such a workspace refuses to log in the same account again and prints the move command.
  - Identity detection in a workspace that has not fetched the site defaults yet uses those of `~/.hearth` (SSO token files, mail domain), and else the mail domain of `~/.hearth`'s login; `hearth identity status` no longer prints an empty identity.
  - `--move-login` accepts a workspace that holds only empty directories (left by `hearth mcp`), and checks it before stopping the daemon.
  - Without a workspace (`~/.hearth`), sessions run inside another `hearth init` workspace are no longer uploaded (they belong to that workspace's login, usually another person's); `hearth session scope` lists them, `scope all` still takes everything.
- Machines show up in Codex Desktop, VS Code and Cursor: on a Mac (or wherever `hearth ssh config` was run once; `[ssh] config`) setup and the daemon keep a Host entry per machine in `~/.ssh/config`, with Hearth's known_hosts, so `ssh <host>` and the apps' SSH lists work without writing config or accepting host keys by hand. Hosts are named `[family]-[host]-[hardware]-[node]` (e.g. `gb-johor-edge-gpu-e05-13`; `[ssh.aliases]` renames one), the same names `hearth ssh`, `hearth machine list` and every command accept. This machine is left out; two Hearth homes on one machine (`~/.hearth` and a workspace) are listed once. `onboard status` has a `ssh-config` step when entries are missing.
- Fixes from a Mac user's first days (Mac and managing GPU machines from it):
  - Shell lines are kept per operating system (`shell-zshrc.darwin` on a Mac): Linux rc lines (`export HOME=/root`, cluster `JAVA_HOME`, `PATH=/root/...`) no longer reach a Mac, and the Linux snippet older versions sourced there is taken out. On every machine, lines setting `HOME`, `USER`, `LOGNAME`, `SHELL`, `PWD` or `TMPDIR` are never applied; assignments naming absolute paths that do not exist here are guarded (lists such as `PATH` lose the missing entries). Restored snippets of older versions get the guards in place (daemon). New `hearth shell restore --dry-run` and `hearth shell uninstall`; a block whose line the user commented out is left alone.
  - Recipe env values that are paths are exported only where their directory exists (`GIT_CONFIG_GLOBAL=~/bootstrap/vault/gitconfig` on a Mac without it no longer hides the git identity).
  - Recipe steps whose commands use `${WORKSPACE}` are skipped ("needs a workspace") on machines without one, instead of checking `/.ssh/config`.
  - `hearth lib mcp-install` registers with Claude Code through `claude mcp add-json` (its variadic `-e` swallowed the server name: "Invalid environment variable format: hearth"); a failed registration prints the command to run by hand.
  - Network: connections fail after 10 s instead of hanging; a timeout without a proxy in the shell says so; the daemon remembers the proxy it reached the server with, and hearth commands started without one (`hearth ssh <machine> -- hearth ...`) use it.
  - `hearth ssh -t` gives the remote command a terminal (QR-code logins); the client's own SSH log lines are quiet.
  - Machine names work the same in every command (full name, short name, id prefix, unique part); `hearth machine list` hides revoked machines (`--all`) and shows when each was checked; `hearth ssh` lists `ssh hearth-<machine>` (with host keys, after `hearth ssh config`) instead of a raw `ssh -p` line that failed host-key verification.
  - `hearth recipe done` / `run` report the environment at once.
  - The codex-mixin import step runs `codex-mixin doctor` afterwards and fails when it is not ok; a new interactive step `codex-mixin-login` covers a provider that needs this machine's own login.
  - `hearth init` says when the workspace is not logged in yet and offers `--move-login` (moves the login and state of `~/.hearth` into the workspace and repoints skills, MCP and hooks).
  - Setup ends with how to make `hearth` available in the current terminal when its directory is not on PATH yet; the installer also links into `/opt/homebrew/bin`.
- Agent CLIs are recorded without a version: new machines install the latest Codex CLI / Claude Code instead of the version the first machine happened to have (`[[tools.pin]]` with a `version` still holds one back; `hearth tools add <name> --version x.y.z`).
- Commands Hearth runs (`codex-mixin doctor`, recipe commands and checks) get `localhost`, `127.0.0.1` and `::1` added to `no_proxy` / `NO_PROXY` when a proxy is set: on machines with `http_proxy` but no `no_proxy`, codex-mixin's local gateway answered `502 Bad Gateway` from the proxy and the environment check reported it as down. The "newer Hearth" finding uses the version in the report, so it no longer shows right after an update. On macOS the CLI bundled in the Codex app (`Codex.app/Contents/Resources/codex`) counts as Codex installed.
- Environment check: tools installed after the daemon started (in `~/.local/bin`, nvm's Node, `~/.npm-global/bin`, …) are found; the daemon adds the user's install directories to its PATH, after its own entries. `hearth machine check` reports this machine's environment at once (the daemon does it every 5 minutes). `codex-mixin doctor` (it asks the provider for its models, sometimes for half a minute) runs in the background at most every 15 minutes, and a doctor that did not finish is no verdict instead of a failed check.
- Machine environment check against the client setup guide: each client reports the versions of Codex CLI, Claude Code, codex-mixin and Node, `codex-mixin doctor`, the agents' Hearth integration and the restore steps left; the server looks up the latest releases (npm registry, GitHub release feed, every 6 hours, `--no-version-check`, `$HEARTH_NPM_REGISTRY`) and judges each machine (missing, N releases behind, check failed, not connected, steps left, newer Hearth). The console's Machines page has an Environment column (green / amber / red pill, hover card with the problems, click for the tools table, fixes and the sentence to tell an agent); `hearth machine list` shows the same.
- New-machine fixes from a real install on a shared account: only the user's own Comate login (`~/.comate/login-user/<user>`) is recorded and restored, and other people's logins recorded by older versions are dropped from the learned recipe; restore prints one line per reason for skipped workspace files and notes instead of one per file, and ignores the uncommitted-work snapshots of older versions; restored rc lines that call a version manager or prompt tool missing on the machine (`conda`, `pyenv`, `nvm`, `starship`, …) are guarded with `command -v`, so new shells no longer print "command not found"; the sshd Hearth starts uses `LogLevel=INFO` (images with `LogLevel DEBUG` printed sshd debug lines into SSH sessions) and an older Hearth-started sshd is restarted with the new options; the daemon installs the hearth skill for agents installed after setup.
- Docker image `ghcr.io/hearth-project/hearth` (linux/amd64 and linux/arm64) published with every release and used by the compose files; CI builds it and starts the server when the Docker files change. Release notes now start with the version's CHANGELOG section. Repository files for contributors: pull request template, issue template chooser, CODEOWNERS, CODE_OF_CONDUCT.md, SUPPORT.md.
- SSH between the user's machines, authenticated by Hearth (on by default on Linux). Each device gets its own ed25519 key; its public key and the user's usual `~/.ssh/id_*.pub` keys (`[ssh] share_keys`) are kept as end-to-end encrypted secrets, and every machine writes the keys of the account's active devices into a marked block of `~/.ssh/authorized_keys` (lines added by hand stay). The daemon keeps the system sshd running the way GPU containers are set up by hand (`sshd -D -e -f /etc/ssh/sshd_config -p 8022 -o ListenAddress=<bond0 or main interface>`, public keys only, `AllowUsers` = the user, detached with setsid); an sshd already listening on the port is used as it is. Machines publish their address and host key, so `hearth ssh` verifies them. `hearth ssh [machine] [-- cmd]`, `ssh enable|disable [--all]|status|keys|authorize|unauthorize|config` (`Host hearth-<machine>` entries in `~/.ssh/config` for IDEs, refreshed by the daemon); `hearth status` shows it; revoking a device drops its keys everywhere within a minute. `[ssh] enabled`, `port`, `address`, `share_keys`.
- Long-term memory. Every conversation gets a memory card while it syncs (goal, outcome, later requests, errors, commands, files; extracted without model calls) carried encrypted in its metadata, so every machine indexes every machine's conversations without downloading them. A local SQLite FTS5 index (shared CJK/English tokenizer, BM25 with recency, kind and directory boosts, common terms pruned) also holds remembered facts (end-to-end encrypted secrets `memory.<id>`) and the agents' own memory notes; searches take a few milliseconds and never use the network. `hearth recall <words>` (`--show`, `--json`), `hearth memory remember|forget|list|index|status|hooks on|off`; MCP tools `recall`, `remember`, `forget`. Codex and Claude Code get a `UserPromptSubmit` hook that adds up to 3 clearly related memories to each prompt (about 15 ms including process start) and a `SessionStart` hook with the remembered facts; Codex asks once to trust it. The daemon updates the index every 5 minutes; `[memory] enabled`, `hooks`.

## 0.1.0 — 2026-10-29 (first public version)

- README in English by default (`README.md`; Chinese: `README.zh-CN.md`), reorganised around a quick start with separate one-command server and client deployment. New `scripts/deploy-server.sh`: installs the latest release (or builds from source), creates a self-signed certificate, starts the supervised server and prints the client install command; re-running upgrades.

- Uncommitted-work snapshots removed: Hearth no longer snapshots git repositories (`hearth wip`, `@wip`, `[workspaces]` and `--wip-interval` are gone; old settings are dropped from config.toml). Code goes through git as usual.

- Setup no longer installs software: it restores data and credentials (login, hearth skill, conversations, library, credential and config files, env, shell lines) only. Software and commands of the restore recipes form this machine's restore flow, `hearth recipe plan [--json]` (in recipe order, with a check per step; tool pins of config.toml included), which the hearth skill goes through with the user (new section D: check, install following the guide, check, `hearth recipe done <key>`, record what this machine needed differently); `hearth recipe run <key>` runs chosen steps. New client software guide `docs/{zh,en}/client-env.md` (Node, Codex CLI, Claude Code, codex-mixin: install, check, where the latest versions are), printed by `hearth docs env` together with the server's notes (`site/files/client-env.md`). The server keeps no install packages. codex-mixin's config backup works again (`config export` / `import` take a file path; recorded steps are migrated) and its restore no longer needs a QR-code login on new machines.


- Recording without `hearth learn`: the background sync (every library interval) and setup record new findings with learn's proposal (machine-specific ones for the machine's profile), copy new skills and agents of the agents into the library, and keep credentials automatically once the user says yes (setup asks once; `[learn] auto_credentials`, `hearth learn --auto-credentials`). Changed copies and env values with a password in a URL are left to `hearth learn`; `hearth status` counts only what needs a choice. `[learn] auto = false` turns it off. Hearth's own MCP entry no longer makes a recorded Codex `config.toml` look changed, and setup registers the MCP server after restoring it.
- Shell environment: the user's own statements of `~/.bashrc` / `~/.zshrc` (compared with `/etc/skel` and stock distribution defaults; tool-managed `# >>> ... >>>` blocks and Hearth's blocks left out) and `~/.bash_aliases` are kept as encrypted secrets and merged across machines; a new machine gets them in `<hearth home>/shell/*.sh`, sourced from a managed block of its rc file (only inside the workspace on a shared account), without paragraphs its rc already has and with `source` lines of missing files neutralised. `hearth shell show|save|restore`, `[shell] sync|files`.

- Smoother new-machine setup: setup copies the skills and agents the machine already has into the library (once per machine, so a skill deleted from the library is not brought back; items that look like they hold a credential are listed and left out; `--no-import`); asks for the account email in a terminal when no local identity is found; offers the conversations left on machines still online (usually the machine being replaced) instead of only a hint; a clearer message when a login fails (wrong password or new account); the hearth skill hint is printed once; ends with a `done:` summary and only the next steps that apply (the container hint only in containers).

- Team items get invoked automatically: each team's 20 most used skills and 20 most used agents (ranked by its members' use; `GET /v1/teams/{team}/packages` now returns `uses`/`users`, hottest first) are linked on every machine of a member and rendered into all agents, resident list or not (`[teams] use_top`, `use_exclude`; `hearth team use-top [--dry-run]`; the daemon follows new versions and drops items that fell out). Linked skills are now always rendered (before, a resident list hid them). The skill-search MCP lists team skills in `list_skills`, describes itself as covering the teams, and on-demand team skills count toward the team ranking.

- UX round: `hearth recipe done [id]` marks manual steps done on this machine (and `done_when` checks run in dry runs); warnings no longer fail `recipe apply`; `hearth learn --later` (or `l` in the checklist) snoozes the reminder for 30 days; `hearth status` shows a newer server build and the other machines online; the daemon checks for new builds every 30 minutes; `session list --wide`. Console: item details (full SKILL.md, files, versions), "keep in all my agents" for team items, "My settings" (resident skills, automatic sharing, links), team updates of the last 7 days, an install command to add a machine, conversations per machine, old-client hint, "remember this computer" (7 days), a compact actions menu for admins; version charts count devices seen in the last 24 hours. Console changes are queued and applied by the user's daemon within about a minute (`/v1/intents`).
- Web console at `/app` for every user (redesigned UI: sidebar, cards, charts, sign-in page): own machines, library skills and agents (most used first; one-click sharing to teams, secret scan first), usage, teams with members and their shared skills and agents in two columns ranked by the members' use, invite codes; admins also get the administration pages. `hearth panel` works for every account; the landing page links to the console.
- Agent usage is counted like skill usage (Codex `spawn_agent` agent types, Claude Code `Task` subagent types; built-in roles not counted) and ranked per account (`hearth lib stats --server`, panel "top agents"). Each user's 5 most used skills and 5 most used agents of their own library are shared with every team where they can publish, and republished when changed (`[teams] share_top`, `share_exclude`; `hearth team share-top [--dry-run]`).
- The default restore leaves out conversations last written on machines that are still online (daemon heartbeat every minute, offline after ~15 minutes of silence or at once on a graceful stop): it brings the 10 most recently active of offline machines. Lists mark online machines with `●`; ids, picks and `--include-online` still restore them. Server: `devices[].online`, `POST /v1/devices/self/heartbeat|offline`.
- Admin panel at `/admin` (no build step, no external assets, en/zh): dashboard with daily active users, uploads and sign-ups, top skills and client versions; user management, sign-up approvals (new registration mode `approval`), invites, teams, runtime settings stored in the database (registration, default quota, client auto-update), maintenance and an audit log. Admins: `hearth server admin grant <email>`; sign in with the account (email + master password; the browser derives the login key with a bundled Argon2id/BLAKE2b/SHA-256 implementation, so the password is never sent) or a link from `hearth panel` / `hearth server admin link`. Clients now send their version; the panel lists active devices (machine, IP of the last request, user, version) and each user's clients online now, admins create teams and manage their members, and shows who uses each top skill and which machines run each version on hover; uploads are counted per day in memory and flushed every minute.
- Teams made usable: invite codes (`hearth team invite` / `join`, default role maintainer, expiry and use limits; only hashes stored), `hearth setup --team <code|name>` (setup asks once in a terminal when the user has no team), `hearth team share <team> <items...>` publishes from the library, `hearth team share-with <team> <other>` lets another team's members read (not publish) a team's skills and agents, `hearth team leave`. Teams the user is in or can read become trusted sources automatically (and stop being sources when left). `hearth status` shows the teams.
- `hearth lib usage prune` deletes the account's usage counts of skills that no longer exist (deleted, renamed, test skills; `--dry-run`, or name them); machines only upload counts of skills they have (library, links, the hearth skill, skills installed in an agent), so pruned names do not come back. Server: `POST /v1/usage/prune`.
- Lighter setup: `hearth learn` shows one checklist with a proposal per finding and saves on Enter (`--one-by-one` for the old per-item questions). `hearth recipe apply` and `setup` list the unapproved commands and ask once; a command approved on one machine runs on the user's other machines (approvals in the encrypted vault; `[recipes] share_approvals = false` to opt out).
- Fewer top-level commands: sharing (`find`, `link`, `unlink`, `links`, `update`, `publish`, `source`) lives under `hearth lib`, agent import under `hearth agents import`; `onboard`, `agent`, `save`, `env`, `register`, `identity` are hidden. Old names keep working.
- Restoring a large conversation shows a download progress line. Subagent threads and turn-less fork copies (Codex Desktop copies) are listed under their conversation ("+N sub") and subagents are restored with it; the index records each thread's parent.
- Client UX: `hearth status` is one screen (login, background sync with last check / upload / error from the daemon heartbeat, storage, agents, library, next steps; `--json`). `hearth restore` in a terminal shows a numbered list to pick from (`-i`; `-y` keeps the old behaviour); restore prints one line per conversation with its title instead of per file. `session list` aligns CJK titles, fits the terminal, merges a thread's files, hides empty threads and backup files (`--files`), shortens host names and marks this machine. `hearth --help` is grouped by task. `setup` / `login` take the server from the install command, so `--server` is optional. Network errors say what to check. Titles skip agent-injected context blocks and Codex Desktop attachment headers.
- Fix: a machine holding an older copy of a conversation that another machine continued no longer overwrites the session index (title, turns, last activity) with its stale values.
- End-to-end encrypted, incremental sync of Codex, Claude Code and Comate sessions and memory; leases, expiry, deletion sync (Codex).
- Session index (title, rounds, last update, machine) stored apart from content; search and restore chosen conversations; newest 10 by default.
- Path rewriting between machines; Codex Desktop shows restored threads in the open window.
- Per-agent upload selection (`backup.conf`), credentials and auth files as encrypted secrets, `hearth learn` and restore recipes with machine profiles.
- Cross-agent library (skills, agents, instructions), teams, git sources, skill search over MCP; Claude Code → Codex session import.
- Server: SQLite + directory or PostgreSQL + S3, supervisor, quotas and admin commands, backup / migrate, download page, site defaults for organisation-specific setup.
- New machines restore only recently used agents (`hearth agents pull` for the rest), never replace an installed agent CLI, and do not link a skill the agent already has; `login`/`setup` refuse to replace another account's login without `--switch`.
- The install one-liner for a self-signed server is plain `curl -k …/install.sh | sh` (the installer pins the embedded certificate); `server --pin-install` restores `--pinnedpubkey`.
- One user settings file: `library/config.toml` now holds skills (dir/resident), agents, backup include/exclude, learn ignore, tools, workspaces and MCP; older split files are migrated automatically. `hearth config [--edit]`.
- Skills storage is configurable: `skills.dir` in the library's config.toml, or `hearth lib skills-dir <path>` (moves the one copy, rewrites agent symlinks, syncs with the library).
- setup takes the account from the local identity and, on an open server, creates it when the login does not exist (password typed twice; `--no-register` to forbid).
- Client daemons install new builds from the server by themselves (every 6 h, checksum verified, restart in place); `self-update --auto off` per machine, `server --no-client-auto-update` for everyone.
- One-line installer for Linux / macOS (x86_64, arm64) that installs the `hearth` agent skill.
- `learn` records an SSH identity as one item: the private `ssh.config` it points at, the keys that config references, `GIT_SSH_COMMAND`, and the `sshx` / `scpx` aliases, so a new machine can use git/ssh without a hand-written activation script. `${WORKSPACE}` also expands inside `run` and `check` commands. `doctor` reports a library that stopped syncing because local and server both changed.
- `hearth login` no longer requires `--email` or `--server` when the machine already knows them: it reuses a valid existing login, else picks the account from the local identity (an existing hearth config, `$HEARTH_IDENTITY`, the organisation's SSO token cache from `site/learn.json`, Comate's `login-user` files, `$COMATE_USERNAME` / `$SYS_USER_NAME`), using the workspace name to disambiguate several people on one Unix account. `hearth whoami` shows both. The master password still unlocks the vault.
- Optional passwordless login through a platform identity broker (`server --identity-broker`): while logged in, `hearth login` / `hearth setup` / the daemon start automatically upload the vault key wrapped by the account's platform secret (no command, no manual upload), and `hearth login` on a new machine proves possession of the same secret (the broker resolves it server-side, so the system key never reaches clients). Falls back to the master password when no platform credential matches; `hearth identity disable` opts out and is not undone by the automatic path.
